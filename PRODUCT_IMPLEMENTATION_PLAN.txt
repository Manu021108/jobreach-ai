1. PRODUCT DEFINITION
--------------------------------------------------------------------------------
One-line pitch:
  "Students sign up, connect their own Gmail, pay once to unlock a verified
   5,000+ HR/recruiter contact database, and run safe, AI-personalized cold
   email campaigns to get job interviews."

Who it is for:
  - Primary: final-year / placement-seeking students, bootcamp grads, early
    career job seekers in India (assumption to confirm -- see Open Decisions).
  - Secondary: career cells / training institutes that want to offer this to
    batches (later phase, not in prototype).

Core value:
  - Solve "I don't know who to email and I can't send 500 emails by hand."
  - Give students a warm, trackable outbound job-search pipeline with guardrails
    so they do not get their Gmail account flagged.

Business model (prototype assumption):
  - One-time "Unlock" payment (e.g. INR 299-499) grants lifetime access to the
    5,000+ contact database + a starter campaign allowance.
  - Optional paid "campaign credits" / monthly plan later (do not build now).
  - Sending happens from the student's own Gmail, so the platform has no per
    email cost -- revenue is the unlock fee, not email volume.

2. CURRENT STATE (WHAT ALREADY EXISTS)
--------------------------------------------------------------------------------
Built today (do not rebuild):
  - FastAPI backend (main.py) with ~20 REST endpoints and safety logic.
  - React 18 + Vite SPA (frontend/src/App.jsx) with 6 screens: Overview,
    Companies, AI Email Studio, Campaign & Send, Follow-ups, Settings.
  - SQLite via SQLAlchemy with 3 models: contacts, email_drafts, outreach_events
    (app/db/models.py).
  - CSV/XLSX contact import with dedupe and validation (10 MB cap).
  - AI draft generation via OpenAI-compatible API (Ollama default) with a single
    anti-hallucination system prompt (app/services/ai_writer.py).
  - Gmail API sending with resume attachment, OAuth token file, reply matching
    (app/services/gmail_service.py, app/services/outreach.py).
  - Strong single-user safety rules: DRY_RUN, approve-only, typed recipient
    confirmation, per-run/per-day caps, minimum interval (main.py:142-159).
  - Sample dataset: 82 HR contacts in data/jobreach_company_contacts.xlsx.
  - Basic pytest suite (tests/).

Critical gaps (must be closed for a public paid product):
  G1  No auth, no users, no per-user data isolation (app is single-user/local).
  G2  No payments, pricing, checkout, webhooks, or entitlement gating.
  G3  Only 82 contacts; no 5,000+ dataset, no data pipeline, no provenance.
  G4  Gmail OAuth is one machine-local client + shared credentials/token.json;
      sender profile and caps come from .env and need a restart to change.
  G5  No automation: no queue, no worker, no scheduler; APScheduler declared but
      unused. Follow-ups are reminders only. "Campaign" = single draft screen.
  G6  No resume parsing (only the filename is sent to the LLM).
  G7  No pagination/search; no migrations; no backups; no CI/CD; no deployment.
  G8  Security state is unsafe to expose: .env has DRY_RUN=false, a populated
      Gmail token is committed locally, and the DB has real SENT events.
  G9  No legal/consent layer: opt-out exists in the model but is not surfaced in
      the sending flow; no terms/privacy/refund policy; no deliverability plan.

3. PRODUCT SCOPE -- MINIMUM WORKING PROTOTYPE
--------------------------------------------------------------------------------
In scope (must ship for the prototype):
  1. Student registration, email verification, login/logout, password reset.
  2. Per-user data isolation (every contact/draft/event/campaign belongs to a
     user; no cross-user leakage).
  3. Per-user Gmail connection with a proper OAuth web flow, encrypted token
     storage, token refresh, and a visible "connected" state.
  4. Onboarding: student profile + resume upload, editable in the UI (no .env).
  5. One-time payment ("Unlock") with a real payment provider, signed webhook,
     and entitlement check that gates access to the 5,000+ database.
  6. Curated 5,000+ HR contact dataset with search, filters, verified badges,
     and pagination; locked state shown before payment.
  7. Campaign builder: select contacts -> generate AI drafts -> approve -> queue.
  8. Automated sending via a background worker with conservative daily caps,
     throttling, retries, and per-user progress tracking.
  9. Follow-up automation + reply/opt-out sync into the dashboard.
  10. Student dashboard with clear metrics: sent, opened (if available),
      replied, opted-out, remaining daily quota.
  11. Safety & compliance basics: opt-out in every email, unsubscribe handling,
      dry-run mode per user, legal pages, audit log.
  12. Deployable, monitored, backed-up web app (not localhost-only).

Explicitly OUT of scope for the prototype:
  - Mobile apps, team/company accounts, role-based admin beyond a simple back office
  - LinkedIn automation, WhatsApp/SMS, ATS integrations (Naukri/LinkedIn sync)
  - Runtime web scraping of HR emails (dataset is curated offline)
  - Advanced analytics, A/B testing, warm-up domains, dedicated IPs
  - Multi-language UI, gamification, referral program, coupon engine
  - Subscription billing (one-time unlock only for now)

--------------------------------------------------------------------------------
4. TARGET USER JOURNEYS (HAPPY PATHS)
--------------------------------------------------------------------------------
J1. Sign up and onboard
    Register -> verify email -> set profile (name, skills, target roles, location)
    -> upload resume -> land on dashboard.

J2. Connect mail
    Settings -> "Connect Gmail" -> Google OAuth consent -> token saved encrypted
    -> settings show connected account + "Send test email (dry-run)" option.

J3. Unlock the database
    Browse sample (locked) contacts -> click Unlock -> checkout (Razorpay/Stripe)
    -> payment webhook sets entitlement -> full 5,000+ database unlocked and
    searchable -> receipt/invoice emailed.

J4. Run a campaign
    Filter contacts (role, city, company size) -> select N contacts -> "Generate
    drafts" (background job) -> review/edit/approve -> schedule -> worker sends
    with caps -> live progress -> follow-ups auto-created -> replies synced.

J5. Stay safe
    Recipient can opt out (reply "stop" or link); status flips to OPTED_OUT and
    the contact is permanently excluded from all future campaigns.

6. ARCHITECTURE CHANGES
--------------------------------------------------------------------------------
From: one local uvicorn process, shared .env config, shared token.json, clicks
      send one at a time, SQLite file on disk.
To:   a small deployed SaaS:

  [ React SPA ] --HTTPS--> [ FastAPI API ] --SQL--> [ PostgreSQL ]
                                |                    [ Redis ]
                                +---enqueue---> [ Worker(s) ] --Gmail API-->
                                                        student inboxes
                                +---webhook---> [ Razorpay/Stripe ]

Components to add:
  - Auth: email+password (bcrypt/argon2), signed session cookie or JWT,
    email verification, password reset. Use a library (FastAPI-Users or
    python-jose + passlib); do not hand-roll crypto.
  - Worker + queue: Celery/RQ/ARQ with Redis. Replace unused APScheduler or use
    it only for cron-like triggers. Tasks: generate_drafts_batch, send_campaign,
    schedule_followups, sync_replies, verify_dataset.
  - Progress: jobs table + polling endpoint (SSE/WebSocket is a phase-2 polish).
  - Config: replace .env-only settings with DB-backed user settings + secret
    store (environment/secrets manager for provider keys). Add Alembic.
  - Storage: object storage (S3-compatible) for resumes; never write uploads to
    a local folder in production.
  - Deployment: Dockerfile + docker-compose (api, worker, beat/scheduler, redis,
    db, nginx/static SPA) or equivalent managed services. GitHub Actions for
    test + build + deploy. HTTPS, backups, structured logs, error tracking.
  - Email transport: keep Gmail API per user. Enforce Gmail's consumer limits
    (~500 sends/day; be conservative: default 25-40/day/user) and surface the
    remaining quota in the UI. SMTP can be added later; not needed now.

9. RISKS & MITIGATIONS
--------------------------------------------------------------------------------
R1  Gmail suspension / spam complaints (highest risk).
    Mitigate: conservative caps, plain-text emails, no links in first touch,
    opt-out in every email, warm-up guidance, dry-run default, bounce handling.
R2  Dataset legality/quality: scraping personal emails may violate law/ToS.
    Mitigate: use public company HR addresses or licensed/opt-in sources; keep
    provenance; suppression list; verify before shipping; legal review.
R3  Payment compliance / chargebacks: use a provider, not custom card handling;
    clear refund policy; webhook signature verification.
R4  Data leak across users: enforce user_id scoping in every query + tests.
R5  AI hallucination (fake vacancies/claims): keep the existing strict prompt,
    ground on user-supplied context + parsed resume, human approval required.
R6  LLM cost at 5,000 drafts: batch jobs, caching, cheaper model, quotas.
R7  Scope creep: freeze the Out-of-scope list; ship the checklist in section 8.

As a high-skilled product developer, I have reviewed the jobreach-ai project
  codebase. Below is a report of the critical issues identified and a roadmap for
  future developments.

  Project Overview

  JobReach AI is a local-first, FastAPI + React CRM designed for personalized job
  outreach. The current state is highly functional as a local prototype but requires
  significant work to transition into a robust, multi-user product.

  1. Critical Issues & Technical Debt

  Security & Compliance

  - Plaintext Credentials & Tokens: The credentials/ folder contains sensitive
    token.json and client secret JSON files. These are not git-ignored (although they
    should be) and represent a significant security risk if the repository were ever
    shared or pushed.
  - Database Exposure: The SQLite file (data/jobreach.db) is used for storage. While
    efficient for local development, it is unsafe for multi-user web hosting and lacks
    the concurrency and security features of PostgreSQL.
  - Lack of Auth Robustness: The current implementation uses a single, shared
    AUTH_SECRET_KEY and does not fully leverage secure, server-side encrypted storage
    for sensitive data outside of the database column encryption.
  - Dry Run Defaults: The project correctly defaults to DRY_RUN=true, but managing this
    via environment variables makes it easy to accidentally misconfigure in a
    production deployment.

  Backend Engineering

  - Worker/Task Management: The application relies on threading for background workers
    (job_discovery_worker.py, followup_service.py). This is prone to race conditions,
    zombie threads, and lack of persistence. A robust task queue like Celery, ARQ, or
    Dramatiq with Redis is necessary for production.
  - Scaling & Concurrency: The use of SQLite with multiple threads requires careful
    locking. Under higher loads, this will cause database locks and bottlenecks.
  - Error Handling: Many services perform IO operations (Gmail API, AI API) with broad
    try/except blocks that may mask root causes or lead to "uncertain" states (e.g.,
    Gmail accepted a request but the status was never updated in the DB).

  Frontend & UI

  - Single-Page Application (SPA) Routing: The frontend routing relies heavily on
    client-side state, which is fine for a small tool but needs to ensure strict route
    protection to prevent unauthorized access to API endpoints if the user manually
    tries to navigate.
  - Data Consistency: The frontend relies on a single WorkspaceContext that fetches
    everything on load. For 5,000+ contacts, this will cause significant performance
    lag. Pagination and server-side filtering are required.

  2. Recommended Roadmap for Future Development

  Phase 1: Productization & Scalability (Immediate Priority)

  - Database Migration: Migrate from SQLite to PostgreSQL. This is non-negotiable for a
    multi-user environment.
  - Task Queue Implementation: Replace internal Python threads with Redis-based tasks
    (Celery/ARQ) for all asynchronous operations (email sending, AI generation, inbox
    sync).
  - Server-Side Pagination: Implement robust server-side search and pagination for the
    contact database (HR Database) and campaign views to keep the UI snappy as records
    grow.
  - Asset Storage: Shift from local storage (or database blobs) to object storage (S3)
    for resumes and file attachments.

  Phase 2: Feature Expansion

  - Automated Resume Parsing: Integrate a PDF parser (e.g., PyMuPDF or pdfplumber) in
    the backend to extract skills and experience from the uploaded PDF. Use this to
    automatically augment the student's profile for the AI writer, reducing the manual
    setup time.
  - Advanced AI Matching: Move beyond simple keyword matching to semantic search using
    vector embeddings (e.g., via pgvector or an external vector store) to better align
    candidate resumes with job descriptions.
  - Deliverability & Analytics: Add detailed bounce handling, open-rate tracking (via
    standard pixel integration), and domain reputation monitoring to help users stay
    out of spam folders.

  Phase 3: Platform Features

  - Team/School Accounts: Add an organization entity to allow career cells to manage
    batches of students, track collective placement statistics, and provide curated
    contact lists to their students.
  - Advanced Integrations: Direct ATS integration (e.g., syncing application status
    from Workday/Greenhouse) would be a game-changer for users.

  ---

  How to apply this report

  - Security: Immediately add credentials/ and data/*.db to your .gitignore and rotate
    any leaked secrets.
  - Data: Start prototyping a PostgreSQL migration and test it using a staging
    environment.
  - UX: Prioritize implementing server-side pagination for the "Companies" table; as
    you scale toward 5,000+ contacts, the current frontend state approach will fail.

  I have not made any code changes, but I recommend prioritizing the database migration
  and the transition to a formal task queue before attempting to scale the user base.

Implementation note (2026-11-19): The threading/APScheduler workers described above were replaced with Celery workers plus Redis. Celery Beat owns the periodic auto-send, follow-up, and job-discovery schedules; the FastAPI app no longer starts background threads. Redis broker/result settings and worker/beat commands are documented in README.md. Use a persistent Redis instance and run a single Beat process in production.

Implementation note (2026-11-19): The SQLite persistence layer was replaced with PostgreSQL plus Alembic migrations. Compose files provision PostgreSQL and Redis, launchers apply ``alembic upgrade head`` before starting the API and Celery processes, and the SQLAlchemy session uses a pooled psycopg 3 engine with connection pre-ping. SQLite remains available only for tests and legacy local overrides.
